## 1. What each piece does, and current state

### `onetrip-driver` — the driver-facing app

**OneTrip** (formerly called "OneJob" — fully renamed) is a mobile-first PWA that eliminates "pencil whipping" (drivers falsely certifying a pre-trip inspection without physically doing it). It forces a driver through a structured, phased checklist with live-camera-only photo evidence (no gallery picker — a photo must be taken in the moment), then uploads everything to a company-controlled Google Drive as a permanent record.

**The inspection flow, in order:**
1. **Setup screen** — truck number (a **dropdown**, restricted to a known-trucks list — see below), driver name, date
2. **Phase 1 — Engine Off**: zone-by-zone stations under the hood, each with sub-items that are Pass/Fail/N/A toggles, HAND-entered numeric readings (some with auto-computed pass/fail thresholds, e.g. tire tread depth), and/or a required station photo. **The very first station of the whole walk (added 2026-09-12) is `1-door`** — a photo of the driver-door DOT number placard plus a typed text value (`mode: 'text'`, a new sub-item control alongside the existing toggle/numeric ones), so the number only has to be entered once; Station 12 in Phase 3 auto-populates from it (see section 2's 2026-09-12 entry)
3. **Transition screen** — instructions to close the hood, start the engine, turn on lights, exit the cab
4. **Phase 2 — Full Exterior Walk**: same station/sub-item pattern, walking the whole truck+trailer exterior (9 zones)
5. **Phase 3 — In-Cab Finale**: dash, air brake system readings (Station 11 — all numeric, no photo), cab equipment/documentation
6. **Summary screen** — total items, flagged-fail count, list of any failed items, then **Certify & Complete Inspection**
7. **Complete screen** — plays a draw-in ring+checkmark animation, shows upload status, and offers review/reset controls

Stations unlock **in order** within each phase (you can't skip ahead) — this is intentional, forcing the physical walk order.

Once certified, the record locks: no toggle, numeric field, or photo can be changed, and re-opening any phase screen switches to a read-only view.

**Truck selection is now a closed dropdown, not free text** (added this session) — see `KNOWN_TRUCKS` in `js/data.js`. Currently lists `826016` (Dan's Mack Pinnacle) and `TEST001` (an obviously-fake entry reserved for testing). No free-text entry, no "other" option, by design — a truck not on the list simply can't start an inspection. To add a real truck: add a string to that array, nothing else changes.

**There is no settings control of any kind anymore** — the capture-sound toggle that used to be the app's one settings item was removed entirely this session, at the user's request. No sound plays on capture; there is no toggle to bring back.

**Access**: the live app sits behind a shared passcode gate (`js/auth.js`, hash-compared, not a real secret — see section 3). It is a **public** URL with a public GitHub repo behind it; the passcode is the only thing standing between a random visitor and submitting fake inspections into the real company Drive. **Correction (2026-10-11):** this line used to say no session had ever known the actual passcode. Verification of the gate is done via its wrong-code error path, or (for testing further into the app) by directly setting the same `localStorage` flag the gate sets on success, in an isolated test browser only. The passcode is weak by design (a short shared code that's easy to guess). It's a speed bump, not access control, and any upgrade belongs with the per-fleet auth work in section 7.

### `onetrip-mechanic` — the mechanic portal (Phase 6, discovered 2026-09-13)

A third, separate app, **built entirely in a different, parallel Claude Code session** — not built or tracked by any session this file previously documented. Signs in directly to Google (same pattern as `onetrip-admin`), but confirmed against its own `js/auth.js`: it requests the full, unscoped **`drive`** scope (not `drive.readonly` like `onetrip-admin`, and not the backend's narrowed `drive.file`) — Google's most sensitive, most-scrutinized tier — because it needs to both read across the whole folder tree and write a resolution back, and `drive.file` can't see a pre-existing folder it didn't create itself. Worth knowing if `onetrip-mechanic`'s own OAuth consent-screen status/verification question ever comes up alongside the other two apps' (see this file's OAuth scope-tier notes in section 3).

Three screens, all built and confirmed live: **Screen 1 — Open Defects Dashboard** (flat worklist, one row per open defect, oldest-first — no OOS/MECH severity tag exists yet to sort by, see below), **Screen 2 — Individual Defect View** (photo, full detail, repair notes, optional proof photo, Certify Fixed), **Screen 3 — Resolved History** (full-tree walk of every inspection ever recorded, since a certified fix lives in whatever inspection was "most recent" *when it was certified*, not necessarily a truck's current most-recent one).

Writes a `resolution` object onto the specific failed sub-item at `stations[stationId].subItems[].resolution` — `{ fixedBy, fixedDate, repairNotes, repairPhoto, status: 'repaired', resolvedAt }` — via a read-fresh-validate-merge-write pattern (never a blind overwrite from a possibly-stale in-memory copy). `onetrip-driver`'s own acknowledgment gate (2026-09-13, above) adds `acknowledgedBy`/`acknowledgedAt` onto that same object once a driver has seen it.

Two known write-safety gaps, found during that repo's own Phase 6 sanity pass and accepted as low-priority under today's single-mechanic usage (see `onetrip-mechanic/PROGRESS.md` for full detail, not restated here): a lost-update race if two *different* sub-items on the same inspection are certified from two concurrent sessions, and an orphaned duplicate proof-photo if a photo upload succeeds but the immediately-following JSON write fails.

**OOS/MECH severity tagging was deliberately deferred, not guessed at** — `inspection-data.json` has no such field today, and inventing a classification without real FMCSA Out-of-Service Criteria review was rejected as the wrong call. Sorting is by days-open instead, until Dan/Kevin review real criteria. Tracked as a future task against `onetrip-driver`'s own station data, not this repo — see section 6.

### 2026-09-12: Dan's first-day beta bug fixes

Dan completed his first day of solo field testing and reported four bugs/UX gaps. Investigated the existing camera-capture component, state/data model, and station config first, per explicit instruction, before writing any code — all four fixes reuse existing patterns (no new state layer, no new file, no new component abstraction beyond one new sub-item render mode described in item 3 below).

1. **Flash not firing on photo capture** — root cause: the app never actually requested torch/flash control at all, so it was guaranteed not to work regardless of device. `openCamera()` (`js/app.js`) now detects real torch support via `MediaStreamTrack.getCapabilities().torch` once the stream resolves; a "Flash" toggle button in the camera control row calls `applyConstraints({advanced:[{torch}]})` where it's supported (mainly Android Chrome with a real rear LED flash). Where it isn't (all of iOS Safari, some Android hardware), the button reads "Flash unavailable" and is disabled — visible feedback, not a silent no-op. Deliberately did **not** add a fake "screen-flash" fallback: that trick only helps a *front*-facing camera (the screen has to face the same direction as the lens), and this app always shoots the rear camera, so a bright-screen overlay would light up the driver's own face, not the truck.
2. **No landscape rotation for camera capture** — root cause: `manifest.json`'s `"orientation": "portrait-primary"` hard-locks the installed PWA to portrait everywhere, including the camera screen. Fixed by having `openCamera()`/`closeCamera()` call the Screen Orientation API (`screen.orientation.unlock()` / `.lock('portrait-primary')`) to unlock rotation only while the camera overlay is open — every other screen stays portrait-locked exactly as before. Feature-detected and try/caught throughout, since this API doesn't exist on iOS Safari at all (silent no-op there). Confirmed captured photos need **no** separate orientation-metadata fix: capture works by drawing the live `<video>` element (which browsers already auto-rotate for display) onto a canvas, not by saving a raw file with EXIF tags — so there's no "sideways JPEG" failure mode in either orientation, nothing to code around.
3. **DOT door number captured twice** (Phase 1 photo, then retyped in Phase 3) — investigation found no existing station matched the report at all (no door-placard station existed anywhere in Phase 1; Station 12 in Phase 3 was photo-only, no typed value stored anywhere in the app). Flagged this mismatch and asked before building anything; the user chose to add a real new Phase 1 station rather than reuse an existing one. Added `1-door` (`js/data.js`) as the very first station of the whole walk — photo + a typed text value via a new `mode: 'text'` sub-item control (`renderTextControl()` in `js/app.js`, mirroring the existing un-thresholded `mode: 'numeric'` control: toggle and typed value side by side, no OCR, no parsing). Station 12 now auto-populates from that value at the Phase 2→3 transition (`seedDotNumberFromDoorStation()` in `js/state.js`, called once at the "Proceed to Phase 3" button — the one point the app's forced walk order guarantees `1-door` is done and Station 12 hasn't been touched yet), while staying fully editable for a correction. ## 3. Key architecture & tech decisions, and why

### Frontend (`onetrip-driver/`)
- **Static PWA, vanilla JS, no framework, no build step, no bundler.** Deliberate — keeps the whole thing deployable as a plain GitHub Pages static site.
- **Rendering is now a hybrid of two patterns, and this distinction matters for anyone touching either.** Screen navigation, numeric/text field blur, photo capture, and certification all still go through the original `render()`/`performRender()` full teardown-and-rebuild (no virtual DOM, no diffing) — `render()` always defers that rebuild to the next animation frame (`renderScheduled` flag), which is itself the root-cause fix for a scroll-jump bug that got patched symptomatically twice before finally being fixed at the actual mechanism (see section 2's 2026-09-12 "root-caused for good" entry). **Pass/Fail/N/A toggle taps are the one exception**: `updateAfterToggleTap()` patches the DOM directly and never calls `render()` at all, for exactly the reason those taps are the highest-frequency interaction in the app. The full-render functions (`renderToggleControl`/`renderSubItemRow`/`renderStationCard`) and the targeted-update function are both marked with explicit "KEEP IN SYNC" comments cross-referencing each other — a future change to what a toggle button or its knock-on effects (fail-note, station pill, next-station unlock, progress bar, footer CTA) look like must be made in both places, or a live tap and a fresh page load will disagree about what the same state should look like. This was a deliberate, incremental choice, not an all-or-nothing rewrite — numeric/text fields and navigation are lower-frequency and were left on the simpler pattern.
- **State**: one in-memory `inspection` object (`js/state.js`), persisted to `localStorage` on every change. Only tracks **one inspection at a time** — starting a new one wipes the old (with a hard confirm-guard if it hasn't finished uploading yet). There is currently no multi-inspection history anywhere, which is why streak/completion-time tracking doesn't exist (see section 5).
- **Photos** live in **IndexedDB** (`js/photoStore.js`), not localStorage — a couple dozen real camera photos would blow past localStorage's ~5-10MB quota.
- **Camera capture is live-only** — `getUserMedia` + canvas snapshot, deliberately with no file-picker fallback, so a driver can't select an old gallery photo instead of shooting the truck live. **Cannot be tested from this Claude Code environment's Browser tool at all** — camera access is blocked outright by that tool, with no fake/emulated device fallback available. Any future camera-path change needs a real device to verify.
- **Baseline reference photos**: confirmed "gold standard" framing photos for truck 826016 (`js/baselineReference.js`, images under `assets/baseline-photos/826016/`) are shown as a fixed, non-toggleable 40%-opacity overlay during live capture, one per inspection zone. These photos live as static files in this repo, **not in Drive** — `onetrip-admin`'s Baseline Comparison screen (Screen 4, built 2026-09-12) reads them directly from this repo's public GitHub raw content for exactly that reason; see this file's `onetrip-admin/` architecture notes below.
- **Known trucks**: `KNOWN_TRUCKS` in `js/data.js` — a plain array of truck-number strings, checked at the very top of the file in its own clearly-commented block. Currently `['826016', 'TEST001']`. This is the *only* place a truck needs to be added to make it selectable on Setup.
- **This app reads from Drive for the first time as of 2026-09-13** — every prior version of `onetrip-driver` only ever uploaded. `js/drive.js`'s `checkResolutionsForTruck()`/`acknowledgeResolutions()` call two new actions on the *same* backend the upload path already uses (see the backend's own architecture notes below) — no new credential, no Google sign-in ever shown to the driver, same as always. Both calls fail open by design: Begin Inspection's `onclick` (`js/app.js`) proceeds into Phase 1 regardless of whether either call succeeds, since nothing is ever marked acknowledged unless the backend write actually completes — a failure just means the same items resurface next time, never a silent loss.
- **Service worker** (`sw.js`) caches the static app shell for offline use — cache-first for same-origin GET requests. Its `CACHE_NAME` has a version history in its own header comments (`v5` through `v22` as of this writing) — **read that history before touching this file**, it documents two real, repeated bugs (the CDN-propagation-race that took until `v9` to actually fix, and the missing `controllerchange` listener that took until `v20`, see section 4) and their eventual fixes.

### Drive upload backend (`onetrip-drive-function/`)
- **Google Cloud Run function** (2nd-gen "Cloud Functions," created via Cloud Run's own "Write a function" flow). ESM (`"type": "module"`), using `@google-cloud/functions-framework`'s `http()` registration.
- **Entry point name is `uploadinspectionfile`, all lowercase** — the Cloud Console's "Function entry point" field silently force-lowercases whatever you type.
- **Local git repo since 2026-10-11, no remote, no CI/CD.** Deployed purely by copying `index.js`'s full contents and pasting into the Cloud Run console's Source tab, then clicking Deploy. Git here only records history: a commit does **not** deploy, and a deploy doesn't create a commit, so they can drift. Commit right after each console deploy, with a message saying it was deployed, so `git log` stays an honest record of what's live. The first commit (`a36e330`) is the code as last deployed 2026-09-13. A `.gitignore` excludes `node_modules/` and `.env*`. No credentials are in `index.js` (all come from Secret Manager via env vars), but still keep any future GitHub remote **private**.
- **Auth chain for Drive access**:
  1. `google.auth.OAuth2(clientId, clientSecret)` with `.setCredentials({ refresh_token })`
  2. `clientId`/`clientSecret` come from a **Web application**-type OAuth client, with `https://developers.google.com/oauthplayground` as an authorized redirect URI — unchanged this session
  3. The `refresh_token` was **replaced this session**: the original (obtained once via OAuth Playground, scoped to full `drive`) was swapped for a new one scoped to **`drive.file` only**. To mint one like it: OAuth Playground → gear icon → "Use your own OAuth credentials" → paste the existing Client ID/Secret → in the scope selector, use the **"Input your own scopes"** text box (not the expandable checklist, which can silently also grant the broad `drive` scope if its top-level checkbox is ticked) → enter exactly `https://www.googleapis.com/auth/drive.file` → authorize as `theonetripapp@gmail.com` → confirm the token exchange response's `"scope"` field says exactly that, nothing broader, before using it.
  4. All three values (`DRIVE_OAUTH_CLIENT_ID`, `DRIVE_OAUTH_CLIENT_SECRET`, `DRIVE_REFRESH_TOKEN`) live in **Secret Manager**. Rotating the refresh token means adding a new secret *version*, not creating a new secret.
  5. **Gotcha (still true)**: the Cloud Run runtime service account needs the **Secret Manager Secret Accessor** role on each secret, or the deploy fails with a permission error.
  6. **Gotcha (still true)**: environment variable names are case-sensitive against `process.env.X` and fail silently (not at deploy time) if mismatched.
  7. There is also a vestigial, unused `service-account-key` secret in Secret Manager from the long-abandoned service-account approach — harmless, safe to ignore or delete.
- **Why not a service account**: hard Google Drive API limitation — bare service accounts have no storage quota on a personal (non-Workspace) Google account, so they can never own a file they create. Not fixable with different scopes; don't re-attempt this.
- **Drive folder root is now a hardcoded ID, not a by-name search**: `UPLOAD_ROOT_FOLDER_ID` in `index.js`, currently `1bYVmVsOJU7Rb12akZwSQlEk-YZyFcpfV`. This is deliberate, not a shortcut — under `drive.file` scope, the backend can only ever see files/folders it created itself via the API, so a by-name Drive-wide search (the old approach) is no longer possible at all, and this ID is the folder the backend created fresh for itself under the new credential. **The old root folder and everything under it (including all of Dan's real historical inspections through 2026-09-11) still exists in Drive, untouched, but is no longer reachable through this app.** This was a deliberate, discussed tradeoff — see section 5.
- **`fleetId` now actually flows end-to-end**: the driver app sends it (`FLEET_ID = 'default'` in `js/state.js`), the backend receives and uses it as a cache key (`getDriveClient`), and it appears as a real field in both uploaded files. Still only ever `'default'` — the `TODO(multi-tenant)` lookup that would resolve a real `fleetId` to a different credential/destination is still just a comment, not code, since there's still only one fleet.
- **Drive folder structure**: `<hardcoded root>/Trucks/<truckNumber>/<YYYY-MM>/<YYYY-MM-DD>_<driverName>/`, containing all station photos, `inspection-data.json`, and `inspection-summary.txt`.
- **App-level shared secret** (`X-App-Secret` header): still not a real secret, still a soft speed bump — but note it's necessarily *public*, baked into `onetrip-driver`'s own client bundle (see `js/drive.js`), which is exactly what made it possible to verify the new endpoints directly via `curl` in production with no OAuth involved (2026-09-13) — a real, useful side effect of a value that could never have been secret in the first place.
- **This backend now reads as well as writes (added 2026-09-13)**: two new actions, `checkResolutions` and `acknowledgeResolutions`, added to the *same* `http()` handler/function/URL, discriminated by a new `action` field in the POST body (its absence — every prior caller's request shape — falls through to the original upload behavior, byte-for-byte unchanged). No scope widening was needed for either: `drive.file` already grants access to anything the app itself created, which is all either action ever touches. New read helpers (`findFolder`/`listChildFolders`/`findFileInFolder`/`fetchFileJson`, using the `googleapis` client's own methods rather than the raw REST calls `onetrip-admin`/`onetrip-mechanic` use) mirror those two apps' own established folder-walking pattern. `findUnacknowledgedResolutionsForTruck()` walks one truck's *entire* inspection history, not just its most recent inspection — a resolution can be sitting in an older file than whatever's currently "most recent," since nothing yet stops a driver from starting new inspections before a fix lands (see the OOS/MECH note in the `onetrip-mechanic` section above). `applyAcknowledgments()` groups requested items by file and re-fetches/rewrites each file at most once, since a driver's unacknowledged items can span more than one inspection file.

### Security model, and the OAuth scope/verification picture (mostly new this session)
- **OAuth consent screen is in Testing status**, for the one GCP project (`106361031303`) both the backend's and the admin dashboard's OAuth clients live in. Confirmed directly, not inferred.
- **Testing status means refresh tokens expire after 7 days**, hard rule, no exceptions. For the admin dashboard this just means an interactive re-sign-in every week — mildly annoying, not dangerous. For the backend, it matters more: its refresh token is a static value in Secret Manager with no human in the loop to re-authorize it. **This has not yet been resolved** — publishing the consent screen (moving to "In production") would remove the 7-day expiry entirely, but that likely triggers a Google verification review, whose depth depends on scope sensitivity (see below). ### Original build-time requirements still in force ("OneTrip 1.0", 2026-08-21 → 09-07)
